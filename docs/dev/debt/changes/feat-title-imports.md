# d3d12_x

## add Functional

- [CommandList](../../../core/libs/xdll/d3d12_x/objects/CommandList.cpp) (d3d12_x) - a pipeline whose shader reads constants from its own code (`s_getpc_b64`) gets that shader's whole code container, the store's `.fssm` file found at `<module folder>/../dxbc/fssm/<module name>.fssm`, copied once into GPU-visible memory and passed as the code base in push words 34-35. That the code base is the container's first byte was checked on one shader (the translated constant equals the code's file offset plus the offset after `s_getpc_b64`), not on every shader. A pipeline with two stages that read their own code is skipped, because one push block holds one code base. Code containers are never freed
  Closes when: each stage gets its own code base, or translated shaders carry their constant table themselves
- [IndirectClamp](../../../core/libs/xdll/d3d12_x/commands/IndirectClamp.cpp) (d3d12_x) - checks only that indirect group counts are within the device's limits. Counts within the limits that come from skipped or wrong work still run, and a translated shader that loops on such data runs until the driver resets the GPU. On a device loss the report lists the last eight checked batches as the GPU left them, and for the last 256 indirect mesh batches their groups together, the three largest records and the six newest as records:groups, since the last eight of any kind were recorded after the draw the GPU stopped in (a batch the GPU has not reached shows what an earlier batch left at that place of the checked copy)
  Closes when: translated shaders bound their loops, or the work that writes the arguments always runs
- [CommandList](../../../core/libs/xdll/d3d12_x/objects/CommandList.cpp) (d3d12_x) - a direct mesh dispatch is checked against the device's limits only, so a count of up to 4,194,304 groups runs. One such dispatch was the last checkpoint before a driver reset of the GPU; its group counts were not recorded, and the two translated shaders it ran have no loop whose length comes from memory (the mesh shader's block graph has no cycle, the pixel shader's eight loops each end after at most one pass per lane of the subgroup, its sampler lookup after eight). What made the dispatch run past the driver's time limit is not known. With `ANYBOX_CHECKPOINTS` set the checkpoint of a direct mesh dispatch now carries its group counts, the log names the largest direct mesh dispatch each time it at least doubles, and `d3d12_x.mesh_groups_max` (unset: no limit beyond the device's) skips larger dispatches
  Closes when: a device loss at a direct mesh dispatch is explained from its recorded group counts
- [TitleTextures](../../../core/libs/xdll/d3d12_x/objects/TitleTextures.cpp) (d3d12_x) - the sampled round-robin check (2 ms) and the rechecks a few frames after an upload (3 ms, at most 512) have per-frame time budgets, each texture has at most one queued recheck, and re-uploads found by the refresh share an 8 MiB per-frame budget (chosen, not measured); a texture whose sampled memory changed is uploaded again only once two checks four frames apart read the same samples, because titles stream a texture's data in over many frames and each upload snapshots and detiles the whole texture on the frame's thread (measured 45 ms a frame during a loading screen before this); work over a budget waits for later frames. A texture that is not block-compressed and changed at 16 checks in a row is treated as written every frame (video; block-compressed textures are what titles stream in, not what video decoders write): it is checked every frame, uploaded without waiting for it to settle, and checked once more just before each ExecuteCommandLists so that the uploaded frame is the one the title finished before drawing. Until those 16 checks have passed (about a second) it shows its old content, and a frame the title is still writing at that moment can still be uploaded half written. One re-upload is never split, so a single large texture still costs its full snapshot and detile in one frame. The flushes and the textures hashed whole have no time budget. A diagnostic line every 300 frames splits the time between these parts
  Closes when: memory writes are detected without hashing, or every part has a budget
- [ConsoleDevice](../../../core/libs/xdll/d3d12_x/ConsoleDevice.cpp) (d3d12_x) - `d3d12_x.pipeline_cache` is saved whole each time (hundreds of MiB once a title has built a few thousand pipelines): after 50 new pipelines, after five minutes with any new pipeline, or when no pipeline is queued or building. For pipelines the driver keeps in its own shader cache, the saved data seems to hold only a small reference, so a full or cleared driver cache makes them compile again; unverified
  Closes when: the stats line's "from cache" count shows how many pipelines a seeded run still compiles

- [ConsoleFacade](../../../core/libs/xdll/d3d12_x/objects/ConsoleFacade.cpp) (d3d12_x) - a console object is the table pointer followed by a zeroed area the title owns: 0x4000 bytes for command lists (titles write their own fields there, measured past 0x220), 0x100 bytes for every other kind. AnyBox keeps its own fields in front of the pointer it hands out, and 0x200 pattern bytes (0xA5) after the title area; a changed AnyBox field (checked on every call and when the object is passed to a call) or guard byte (checked at command list Close and Reset) stops with the changed words. How large the title's console objects really are is not measured; a diagnostic line reports the highest byte a title has written in a command list. Command lists themselves sit with their vtable pointer as the last 8 bytes of a read-only page, so a stray write there faults in the writer
  Closes when: the title's object sizes are read from its code, for every object kind
- [ConsoleDevice](../../../core/libs/xdll/d3d12_x/ConsoleDevice.cpp) (d3d12_x) - device slot 76 creates a committed resource with the desktop `CreateCommittedResource` arguments and slot 38 is `GetCopyableFootprints` with the desktop arguments; both were read from one bundled module's call sites (slot 76: heap properties, heap flags, description, a 32-bit state, clear value, interface id, output; what distinguishes slot 76 from slot 27 on a console is not known). A committed texture that asks for a console texture layout is stored in the driver's layout, since its memory has no title address
  Closes when: a second caller of slot 76 confirms its arguments, or the console's own name for it is known
- [Presenter](../../../core/libs/xdll/d3d12_x/vulkan/Presenter.cpp) (d3d12_x) - a present with two planes is composited on the GPU: plane 0 is scaled to the window and plane 1 is blended over it with its alpha (straight by default, premultiplied with `d3d12_x.present_overlay_premultiplied = 1`); `d3d12_x.present_plane` shows one plane instead. The plane layout (0x48 bytes a plane, resource count at +0x08, resource list at +0x10, two 8-dword records at +0x18 and +0x20) was read from one title's presents; which plane is on top, whether its alpha is premultiplied, and what the records hold (they look like source and destination rectangles and a scale) are not measured, so the records are ignored and both planes always fill the window. More than two planes show only the first two
  Closes when: the plane records are decoded and a title with more planes is seen
- [ConsoleObjects](../../../core/libs/xdll/d3d12_x/ConsoleObjects.cpp) (d3d12_x) - pipeline state slot 11 (two arguments and an object output, called by a bundled module) answers `E_NOTIMPL`; what it returns on a console is not known. The one caller seen treats a failure as a size of 0
  Closes when: the method is identified
- [CommandList](../../../core/libs/xdll/d3d12_x/objects/CommandList.cpp) (d3d12_x) - `DispatchX` (command list slot 80) with flag 0x20 takes its counts as threads: the group count is the thread count divided by the shader's thread group size (read from the module's `LocalSize`), rounded up, and a count that ends in a partial group in x runs a second pipeline of the same module in which threads whose global x index is at or past the count return at once ([ThreadLimit](../../../core/libs/xdll/d3d12_x/vulkan/ThreadLimit.cpp)); the count travels in user data register 31. The flag's meaning is another project's reading plus the four call sites in a title's bundled structure builder (counts n x 1 x 1, flags 0x20 and 0x8020); the guard was validated with spirv-val on 54 modules, and no run has reached the path, because the only caller's pipelines are not built. A partial group in y or z stops, flag 0x8000 and the other flag bits are not applied, and the second pipeline is compiled when first needed, on the calling thread
  Closes when: a run dispatches thread counts through it and the results are compared, and the other flag bits are decoded
- [CommandList](../../../core/libs/xdll/d3d12_x/objects/CommandList.cpp) (d3d12_x) - `ClearUnorderedAccessViewUint` and `ClearUnorderedAccessViewFloat` (console list slots 53 and 54, placed by the desktop order after slot 52; slot 53 was seen called by a bundled module, slot 54 was not) fill the whole texture and only when it is a 2D texture with one mip and one layer: the view's own mip and layer are not read, and rectangles stop. A buffer is filled whole with the 32-bit value when all four values are equal (the view's range and format, which decide the pattern otherwise, are not read); unequal values on a buffer stop. The image is assumed to be in the general layout
  Closes when: the descriptor a view handle names gives its mip and layer
- [TitleTextures](../../../core/libs/xdll/d3d12_x/objects/TitleTextures.cpp) (d3d12_x) - textures treated as video are uploaded as one group just before an ExecuteCommandLists, and a group's uploads may take at most 25% of the time (`d3d12_x.video_upload_percent`): after a group that took N ms the next waits 3 N ms. Each upload reads and detiles on the calling thread (68 ms a frame was measured for screen-sized textures before the changes that follow), so video plays at a reduced frame rate while that path is slow. Only the bytes the uploaded mips occupy in the console layout are read (a texture kept without its top mips no longer has its whole memory copied), the detile takes about 1 ns an element (4.4 ns before, measured on a 3840x2160 32-bit texture: 37 ms to 8.6 ms), and a group never waits for the GPU to free staging memory: when the buffer window is full it stages in a buffer of its own. Where a group's time goes was not measured in a title: the `DIAG video-like textures` line now splits it into reading, detiling or copying, and staging, with the number of GPU waits and own staging buffers
  Closes when: a run's `DIAG video-like textures` line shows a group costing a few milliseconds, or the detile runs on worker threads or on the GPU
- [ConsoleDevice](../../../core/libs/xdll/d3d12_x/ConsoleDevice.cpp) (d3d12_x) - when no video memory is left for a title texture, its view gets a null descriptor and the texture is missing on screen until the title creates the view again with memory free; nothing frees memory for it. Other allocation failures still stop, except device slot 133 (next entry)
  Closes when: textures the title no longer uses are evicted under memory pressure
- [ConsoleDevice](../../../core/libs/xdll/d3d12_x/ConsoleDevice.cpp) (d3d12_x) - device slot 133 answers `E_OUTOFMEMORY` and no resource when the device has no memory for the texture it is asked to place (a texture the title fills itself, or a GPU-written one). What a console answers when its memory runs out was not measured. That a title copes was read from one call chain of one title (7952987A v1.0.2.1, disassembly: the caller at exe+0x193e2d4 returns false for a failed result, its caller at exe+0x34c001 then destroys its wrapper and returns no texture, and its result helper at exe+0x4e9b660 treats only the device-removed results 0x887A0005-0x887A0007 and 0x887A0020 as fatal); other callers of the slot were not read. Nothing frees memory before the title is refused
  Closes when: memory AnyBox holds for unused textures and pipelines is released before a title is refused, and the console's own answer is known
- [TitleTextures](../../../core/libs/xdll/d3d12_x/objects/TitleTextures.cpp) (d3d12_x) - a texture that is not hashed whole is checked through at most 256 samples of 16 bytes spread evenly over its title memory. The samples were at least 4096 bytes apart before, so a texture under 1 MiB had fewer (9 for a 128x72 R32_FLOAT texture, 1 for anything up to 4096 bytes) and a change between them was never uploaded; the spacing now goes down to 16 bytes, so textures up to 4096 bytes are hashed whole and larger ones in 256 places. Read from the code, not measured: which title textures this had left stale, what the denser check costs a frame, and whether GPU-written textures kept in step with title memory (small render and unordered-access targets) are now overwritten from title memory more often. A change that falls between samples of a texture over 4096 bytes is still missed
  Closes when: a run shows the per-frame cost and the upload counts of small CPU-filled and GPU-written textures, and CPU-written textures are told apart from GPU-written ones by something better than size and flags
- [TitleTextures](../../../core/libs/xdll/d3d12_x/objects/TitleTextures.cpp) (d3d12_x) - when there is no device memory for a large title texture (2D, 512 or more on a side, more than two mips, not written by the GPU), it is made again with up to three top mips dropped instead of failing, as the title stops on a texture it cannot create. The texture is blurrier while it lives, and video memory use is not otherwise brought under the card's budget
  Closes when: video memory use stays within the card's budget in the world without dropping mips
- [CommandQueue](../../../core/libs/xdll/d3d12_x/objects/CommandQueue.cpp) (d3d12_x) - the command lists of one `ExecuteCommandLists` call are handed to the GPU one submission each (`d3d12_x.submit_per_list`, on by default), because the system's GPU watchdog lost the device in slow world frames where one call held seconds of work. Whether a single list can still take longer than the watchdog allows is not measured, and the extra submissions cost CPU time
  Closes when: world frames run fast enough that no list comes near the watchdog
- [TitleTextures](../../../core/libs/xdll/d3d12_x/objects/TitleTextures.cpp) (d3d12_x) - a diagnostic that replaces texture content: a file named `anybox_fill_floats` beside the executable holding `<width> <height> <value>` (looked for twice a second at a present, then deleted) makes every R32_FLOAT title texture of that size upload with all texels of all mips at that value instead of its title memory, from its next check on; a file without three such numbers turns the fill off and the textures are uploaded from title memory again. It exists to test whether a CPU-written texture (a software occlusion buffer) is what makes GPU culling reject geometry. The title memory is still read and hashed, a filled texture that the title maps directly is copied through a staging buffer instead, and textures of that size created while the fill is on are filled at their first upload. Not run in a title
  Closes when: the culling input it was built for is settled and the diagnostic is removed, or it becomes a documented debugging setting
- [FrameDump](../../../core/libs/xdll/d3d12_x/objects/FrameDump.cpp) (d3d12_x) - a file named `anybox_trace_frame` beside the executable (looked for twice a second at a present, then deleted) traces the next two presents the way `ANYBOX_TRACE_FRAME` traces three, so a frame can be traced in a running title. The dump reads 8-bit and 10-bit color targets, R11G11B10_FLOAT and R16G16B16A16_FLOAT (shown as x/(1+x) with gamma 2.2, with a count of texels that are not finite and the largest value); multisampled and other formats are skipped. The depth target of each traced draw is written as `frame<present>_depth<i>_<image>.bmp` (32-bit float, 24-bit and 16-bit depth; 0 shown black, 1 white, values between as 40 + 200 * value^0.2) with counts of sampled texels at 0, at 1 and between, and each traced `ClearDepthStencilView` logs its depth value; the stencil plane is not read. Textures bound as render or depth targets of a draw are noted, and so are R32_FLOAT and R32_TYPELESS textures found in the first six slots of a traced compute dispatch's descriptor tables (at most 48 a present): each of those is written as `frame<present>_input<i>_<image>.bmp` (mip 0) with one line per mip counting texels at 0, between 0 and 1, at 1 or above, below 0 and not finite, and one line saying whether TitleTextures keeps it in step with title memory (address, bytes, how it is hashed, upload count, last upload frame, changed checks in a row). Such an input is read while the descriptor lock is held and skipped when no view of it is left; a noted target released before the present is still read after its release. Other formats read by compute, and textures written by compute, are not dumped. Traced draws and dispatches end with `| list <id>` (bits of the command list's address) so lines of lists recorded in parallel can be told apart, the `V#` line shows the first words (at most 32 bytes) of the buffer in slot 0 of the first table as the CPU reads them, and a traced `CopyTextureRegion` into a texture logs its destination and source. In an input image values at 1 or above are green on a logarithmic scale from 1 to the largest value (they were all white before, which hid the content of textures that hold distances), every mip of an input up to 256x256 is also written raw as `frame<present>_input<i>_<image>_mip<L>.f32` (rows of 32-bit floats), and each mip after the first gets a line counting its texels that equal the minimum and the maximum of their 2x2 block in the mip before, which shows whether a mip chain the title computed arrives with its mips at the right places; mips with an odd size in the mip before are compared with clamped blocks, so a count below the total is not proof of a wrong layout there. A traced `Dispatch` logs its group counts and the shader's hash in full. Every traced draw and dispatch also logs its root words, the root signature's heap indexing flags and the bound heaps' addresses (`TRACE     user data ...`). When the request file holds a shader hash (8 or more lower-case hex digits), each traced dispatch of that compute shader writes the buffers in the first 96 slots of its root tables, as the CPU reads them at recording, to `frame<present>_buffer_<title address>.bin` (up to 2 MiB each, one file per address and present, 800 files per request) with a `TRACE     buffer of ...` line per slot; buffers a shader reaches through a heap index are not followed. These additions are built but not yet run in a title
  Closes when: the trace also notes unordered-access and copy destinations of every format and holds a reference to each noted texture
- [IndirectClamp](../../../core/libs/xdll/d3d12_x/commands/IndirectClamp.cpp) (d3d12_x) - while a frame is traced, each checked `ExecuteIndirect` batch (compute and mesh) is noted and its group counts, as the GPU left them in the checked copy, are logged at the next traced present (`TRACE indirect ...` lines and one summary line); a count buffer's value is copied beside them. A batch the GPU has not run by then is shown one traced present later or reported as never run, so batches recorded during the last traced frame for a later submit are not shown. Indirect draws that are not mesh dispatches, and everything when `d3d12_x.clamp_indirect_dispatches = 0`, are not noted. Traced direct mesh dispatches log their group counts. Not yet run in a title
  Closes when: a traced run shows the lines and non-mesh indirect draws are noted as well
- [PipelineObject](../../../core/libs/xdll/d3d12_x/objects/PipelineObject.cpp) (d3d12_x) - `d3d12_x.compute_pipelines_on_first_use = 1` (off by default, not yet run) leaves a compute pipeline unbuilt until a dispatch first uses it; that dispatch waits up to 30 s for a pipeline of at most 2 MiB of SPIR-V and is skipped for a larger one, which goes to the front of the one build thread for those. The reason is a measured correlation, not a measured cause: video memory outside textures grew with the number of built pipelines in every run log read (0.14-0.18 GB with 42 pipelines, 1.3-1.5 GB with about 2,100, 2.4 GB with 2,983), and a title creates compute pipelines it may never use. How many a session uses, and what the waits cost at a scene change, are not measured
  Closes when: a run with the setting shows its effect on video memory and frame times, and it becomes the default or is removed
- [PipelineObject](../../../core/libs/xdll/d3d12_x/objects/PipelineObject.cpp) (d3d12_x) - pipelines over 2 MiB of SPIR-V have one build thread of their own, and the other workers take them only when their own queues are empty; urgency is per lane, so a large graphics pipeline a draw waits for can still sit behind large compute pipelines nothing draws with yet. Builds of large pipelines are limited only by the 3 GiB free-commit gate
  Closes when: builds are ordered by what the current frame waits for, across lanes
- [CommandList](../../../core/libs/xdll/d3d12_x/objects/CommandList.cpp) (d3d12_x) - a root signature created with the directly indexed heap flags gets the bound heaps' addresses in the user data words right after its root words: the shader resource heap's first when `CBV_SRV_UAV_HEAP_DIRECTLY_INDEXED` is set, then the sampler heap's when `SAMPLER_HEAP_DIRECTLY_INDEXED` is set. These words were zero before, so every descriptor a shader took by heap index was read from address zero. The place and order are read from a title's shaders, not from the console driver: compute shaders whose header declares the root words plus two user registers read both as heap pointers (32-byte loads from the first, 16-byte loads from the second), and a pixel shader with a 7-word root signature reads them in s15 and s16. That a signature with one flag gets one word is inferred from compute shaders that read a single heap pointer in their last user register; the flags of those signatures were not seen. A flagged signature with no heap of that type bound passes zero. Two signatures that differ only in these flags share one serialized blob and so the flags of the one serialized last. Built but not yet run in a title
  Closes when: a run shows directly indexed textures and buffers arriving, and the single-flag layout is measured from a signature created with one flag

- [TextureReadback](../../../core/libs/xdll/d3d12_x/objects/TextureReadback.cpp) (d3d12_x) - a GPU-written 2D texture placed at a title address (device slot 133) with one mip, one layer, one sample, a render target or unordered access flag, no depth and at most `d3d12_x.texture_readback_texels` texels (1024 unless set, 16384 at most, 0 turns it off) is copied back to title memory, as it is one memory on the console and a title's CPU reads it there (measured on a 1x1 `R32G32B32A32_FLOAT` exposure target whose title memory stayed zero). The copy is recorded in the title's own command list ([CommandList](../../../core/libs/xdll/d3d12_x/objects/CommandList.cpp)): after a barrier that takes the texture out of the render target or unordered access state, after a barrier on a texture the list drew into, and when a list closes with the texture drawn into or left in the unordered access state. It goes to a host-visible staging buffer of the texture's own, followed by a counter word the GPU writes after the copy; before every ExecuteCommandLists and at every present a changed counter has the texels written into title memory in the console tiling order, without waiting for the GPU. At most 64 textures are kept, each logs its first delivery (`texture readback: the GPU's texels of the texture at title address ...`), and a write that fails is logged once and tried again every 60 presents. Textures of 64x64 and larger that a title fills from the CPU are kept in step by TitleTextures and are never copied back, so the two directions do not meet on one image.
